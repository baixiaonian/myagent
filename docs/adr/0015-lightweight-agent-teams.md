# ADR-0015：单一循环上的轻量团队

日期：2026-09-28。状态：已采纳；其中团队累计额度与时限由 [ADR-0018](0018-long-running-tasks.md) 替代，其他决策保持。

## 问题

单个上下文承担多个角色会互相干扰；固定规划/执行或群聊轮询又会把业务决策固化在框架中。团队需要独立工作、直接通信，但不能绕开已有权限、计费、持久恢复和最终交付约束。

## 决策

用户对话的 Agent 是责任主体，同时保留执行能力。只有它创建成员，成员同会话复用。每个成员是独立内部会话，复用 ChatService 和同一个 runAgent；角色、任务、消息和安全共享范围由持久 TeamService 管理。orchestration 只提供纯协调原语，经 contracts 中立端口接入应用，不反向依赖 application。

Kernel 仅增加通用安全输入/完成确认端口。收件箱在完整工具批次落库后交给模型。候选回答遇到未完成成员进入 waiting_agents，最终提交必须收拢团队。创建/回执/消息/检查点的事务边界保证重启不会凭空复制成员或重放动作。

共享项目、资源锁和授权上限；不复制一次批准、不开放成员修改长期记忆。全局公平模型名额与团队共享额度防止创建成员无限扩张资源。模型继续自主决定分工、计划和业务重试。

## 取舍

首版不引入网络 A2A、递归团队、角色模板、自动 worktree 或固定工作流。共享目录不能隔离逻辑冲突，需模型明确文件职责。选取历史是有来源的安全投影，不是克隆主模型私有推理。应用层保存派生团队索引，原执行事实仍归既有仓储。

与固定 DAG、群聊轮询、主规划/子执行的强约束方案相比，这一选择保持接口小、模型自主，并能复用全部现有执行治理。未来可在中立 RunCommandPort 外新增运行时适配，首版本身不声称实现通用 A2A。
