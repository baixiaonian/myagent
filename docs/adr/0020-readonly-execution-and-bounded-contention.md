# ADR-0020：只读执行与可恢复的资源争用反馈

状态：已采纳。日期：2026-09-29。

## 问题

普通 Shell 无法只凭字符串可靠推断资源副作用。全部占项目写锁虽然保守，却使多成员读操作串行；后台进程持锁时等待成员产物会产生相互阻塞。无限队列只显示 running，模型无法协调，且不应通过杀掉任务或恢复总量配额解决。

## 决策

- 将只读意图变成实际受限的执行：readOnly 命令只读 cwd 与声明的额外目录，无网络；OS 沙箱不可用就拒绝。锁范围等于实际读取范围，允许读/读并发。标准模式仅核验过的静态低风险读取自动采用；完全访问必须显式请求该限制。未知普通 Shell 保持项目写锁，不将 allow 规则当成副作用分析。
- 共用锁协调器持有运行中/排队租约诊断。5 秒争用截止只返回未派发的可处理工具错误，不停止整个 Run、不释放他人锁、不自动重试。Trace 与工具反馈给出持锁身份与资源，模型可通过通信和进程工具协调。
- 团队事件等待不占业务槽位或项目锁；存在本 Run 保留项目进程锁时先管理进程再等待。候选最终回答也经过同一检查。复杂 Shell 内部等待依赖仍不能可靠静态推断，不声称实现任意死锁自动恢复。
- 摘要写作目标与实际可容纳的发布上限分离；收齐正常终态与用量后校验。稍长但有效的完整摘要不作废，失败不删除原上下文、不自动再付费。异常采集容量与任务总量无关。

## 权衡

只读沙箱限制的是实际资源访问，模型声明不形成授权。某些会写缓存的查询程序需普通执行，不能假称只读。5 秒反馈可能使合法长锁竞争返回 busy，保留自主协调比无期限隐式挂起更合适；没有增加固定模型轮数和任务总时限。已发布 v1 摘要保持可复用。
