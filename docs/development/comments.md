# 中文代码注释规范

目标：让初次进入项目的人或 AI 能先从文件注释了解职责，再沿关键逻辑理解为什么这样实现。注释与源码一起维护，不能用文档里的一句话代替代码中的解释。

## 文件开头必须说明什么

所有手写代码文件都需要中文文件头，包含实际作用和所在边界。复杂文件补充输入来自哪里、结果交给谁、哪些操作有副作用、哪些能力尚未实现。小型公共入口说明导出对象和依赖方向即可，不机械填充空洞段落。

```ts
/**
 * 聊天用例协调器：连接设置快照、上下文构建、Run 事务和单次模型执行。
 * 历史与事件通过 ChatStore 保存，具体模型实例由 Server 注入。
 * 增量先持久化再供 SSE 读取；这里不直接处理 HTTP 或数据库驱动。
 */
```

文件头放在 import、类型声明或执行语句之前。存在 shebang、编码声明或 HTML doctype 时保留这些语法所需位置，不改变解释器或文档模式。

## 关键代码必须解释什么

| 场景 | 注释应说明的内容 | 当前参考文件 |
| --- | --- | --- |
| 公开类型与契约 | 字段语义、版本、可空值、状态归属和调用方责任 | [contracts](../../packages/contracts/src/index.ts)、[state](../../packages/state/src/index.ts) |
| 开始运行 | 幂等检查为何在前、何时冻结设置、原子创建哪些记录 | [ChatService](../../packages/application/src/chat.ts) |
| 上下文和模型流 | 整轮裁剪、字符预算、一次调用、EOF 与完整结束的区别 | [context](../../packages/kernel/src/context/index.ts)、[runtime](../../packages/kernel/src/runtime/index.ts) |
| 事务与事件 | 原子性范围、revision 与 seq 的区别、迟到写入如何处理 | [SqliteChatStore](../../packages/adapters/src/storage/sqlite/store.ts) |
| 异步生命周期 | 谁发起和持有任务、如何取消、释放资源、丢弃过期结果 | [工作台](../../apps/web/src/App.tsx)、[SDK](../../packages/sdk/src/index.ts) |
| 凭证与错误 | 哪些字段可公开、文件与数据库的提交顺序、失败如何补偿 | [设置](../../packages/application/src/settings.ts)、[凭证](../../packages/adapters/src/credentials/index.ts) |
| HTTP / SSE | 校验位置、背压、游标、订阅断开与后台执行的关系 | [服务装配](../../apps/server/src/bootstrap/index.ts) |
| 测试与脚本 | 构造该场景的原因、证据边界、资源清理范围和副作用 | [集成测试](../../tests/chat/integration.test.ts)、[容器验收](../../scripts/test-docker.mjs) |

注释放在函数、类型或相关分支紧邻位置。较复杂的公开函数可使用 JSDoc 说明参数、返回值和错误；能从签名直接看出的普通参数不必逐个重复。关键约束不能只写在文件头，读到分支时应能看到解释。

```ts
// 同会话只接受不落后于当前 cursor 的快照，避免 HTTP 返回慢于 SSE 时回滚已显示文字。
// 不应写成“判断 cursor 大小”这种逐行翻译。
```

避免空泛的“处理数据”“执行操作”，也不要把未来计划、未经验证的保证或不适用的限制写进注释。可空用量不是零用量，文件权限不是加密，工具目录占位不是工具已实现。相同限制优先在真正拥有该逻辑的位置解释，其他位置注明调用责任。

## 不同文件的处理方式

- TS / TSX / JS / MJS：中文块注释作为文件头，关键语句用 `//` 或 JSDoc。JSX 属性回调中的解释放在函数体内，不能在标签属性之间直接插入 `//`；JSX 子节点使用合法的 `{/* … */}`，避免产生页面文字。
- Python：文件头使用 `#` 或有意义的模块文档字符串，注释放在代码而非 HTML / SVG 字符串内部，避免改动生成产物。纯注释补充优先 `#`，以免改变 `__doc__`。
- SQL / CSS / HTML：分别使用 `--`、`/* … */`、`<!-- … -->`。迁移说明表关系、索引与版本，不借机重写已应用的 SQL 语义。
- Docker / YAML / 环境示例：说明运行位置、持久化和权限边界；不添加未支持的配置字段。
- 严格 JSON 配置、`.nvmrc` / `.node-version` 等版本文件：不插入非法注释，说明集中在 [环境文档](setup.md)、[配置目录](../../config/README.md) 及所属模块 README。
- 生成 HTML / SVG / Draw.io / PNG、依赖锁文件、二进制、缓存和只读上游：不逐个手工加注释；在对应生成器、源模板或知识文档说明来源和用途。历史架构报告仍保留其原始交付字节。

## 随迭代保持准确

1. 新增文件时同时写职责注释；新增关键分支时同时写设计原因和边界。
2. 修改函数、协议、状态或清理流程时重新阅读相邻注释，及时修订或删除过时描述。
3. 提交前审查注释是否与当前代码、协议和 AGENTS 一致，是否含真实凭证或用户数据。
4. 纯注释迭代用语法树、去注释文本或编译结果对比确认没有混入行为变更，再执行 `pnpm verify` 等适用检查。布局 / 输入法等产品行为未变时，不要求反复调用真实模型；若验证发现行为变化，应查明原因并补相应测试。
5. 更新 STATUS 与迭代历史，记录覆盖范围、实际验证和例外。机械统计文件头只证明覆盖，不证明注释内容正确；仍需人工按调用链核对。

目前规范通过开发约定与提交前审查执行，不新增只检查“有没有注释”的业务测试或注释数量指标。相关入口：[根 AGENTS](../../AGENTS.md)、[迭代工作流](workflow.md)、[提交规范](commits.md)。
