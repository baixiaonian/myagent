# Git 提交规范

每个提交应让全新上下文的开发者看懂完成了什么、为什么改，以及用什么证据确认结果。本规范通过开发约定和提交前检查执行，当前未安装 commitlint 或 Git hooks。

## 格式与语言

标题使用 `type(scope): 中文完成项摘要`，冒号后空一格。type 为下表中的英文类型，scope 使用明确的模块或工程范围（如 `工程`、`聊天`、`sdk`、`文档`）。摘要和正文必须用中文描述已完成的工作；标识符、命令、库名称保留原文。标题尽量不超过 72 个字符，不用“更新代码”“修复问题”“WIP”等无法识别结果的描述。

| type | 适用工作 |
| --- | --- |
| chore | 初始化工程、仓库维护、开发约定 |
| feat | 新增用户可用能力 |
| fix | 修复已有行为的缺陷 |
| refactor | 调整结构，保持既有行为 |
| docs | 仅修改文档 |
| test | 仅新增或调整测试 |
| build | 构建、依赖或打包变更 |
| ci | 持续集成配置 |
| perf | 性能改善 |
| revert | 撤销已有提交，注明原提交及原因 |

正文与标题间空一行，记录完成工作、实际验证，以及影响范围或已知限制。纯文案等简单提交可以省略无意义的段落；跨模块功能、修复和历史重写必须有正文。示例：

```text
feat(聊天): 实现本地 Web 多轮流式聊天与会话管理

完成工作：
- 接通 Web、SDK、应用层和模型适配器，支持多轮回答与停止生成。
- 持久化会话和消息，同步协议、维护文档与迭代记录。

验证：
- pnpm verify：通过，注明本次实际测试数量与范围。
- 未执行真实模型验证时明确记录，不用假模型结果替代。

限制：仅支持可信本机单用户，其他 Agent 模块仍为骨架。
```

## 如何划分提交

- 按完成的工作单元拆分，不按目录机械拆分。项目初始化和后续功能开发分别提交。
- 一个功能所需的契约、实现、测试、迁移和知识更新放在同一提交，避免中间提交无法构建或文档宣称尚未实现的能力。
- 独立的修复、功能或重构分别提交；不要夹带无关格式化和临时调试文件。
- 每个提交应能独立通过当时适用的检查；拆分历史时验证中间版本，不能只验证最终版本。

## 提交前与推送后

1. 阅读当前规则并运行 `git status --short`，只暂存当前工作涉及的文件。
2. 同步 STATUS、相关知识页和 history；检查根及相关局部 AGENTS.md。
3. 执行适合变更的验证，通常运行 `pnpm verify`；涉及产品流程时按测试策略补充端到端验证。
4. 检查 `git diff --cached --stat`、`git diff --cached` 和 `git diff --cached --check`，确保没有密钥、数据库、依赖目录、构建产物或研究上游源码。
5. 使用中文完成项编写提交消息。多行消息保存为文本文件，通过 `git commit -F` 提交，避免 shell 转义破坏正文。
6. 在已获授权的范围内推送，核对远端分支与本地 HEAD；不把本地验证通过当作远程 CI 成功。

## 已发布历史的调整

优先追加普通提交。只有用户明确授权时才拆分、合并或修改已推送历史。开始前记录远端分支 SHA 并保存本地 bundle 或备份引用；验证拆分各阶段，并核对最终产品文件与调整前一致。

推送使用 `git push --force-with-lease=refs/heads/main:<调整前核对的远端完整SHA> origin main`，按实际分支替换 main。不要使用普通 `--force`；租约失败意味着远端已变化，重新核对后再决定，不能直接覆盖他人提交。历史重写改变提交 ID，迭代记录应说明重组原因和验证，不伪造过去的提交时间或原始提交边界。
