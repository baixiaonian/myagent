# 2026-09-29：长进程持锁导致工具批次无法返回

## 现场

用户报告 Trace `8a6a5221144e587d684e406d53c6c88a` 长时间不结束。只读核验 Trace、实际进程树和执行记录：一个成员在多个大目录运行 `find ... -exec stat ... \; | sort | head`，逐文件启动 stat，在 `.worktrees` 持续扫描；过滤路径没有剪枝遍历。进程仍活着，持有项目写锁。主任务和三个成员分别停在 `tool.lock_wait`，没有在途模型请求。

关键缺陷：exec_command 返回运行中句柄后保留锁，同批后续调用却等待本 Run 的同一把锁，导致整个工具批次不返回，模型没有机会选择 read_process/stop_process。不是缓存、模型接口或 Trace 页轮询故障。经 PID、PGID、父 Worker 和持久命令逐项核验后，只向这条只读扫描进程组发送 SIGTERM；任务随后从主第 12 步继续到 26 步，已有成员完成，未重放模型/工具。

## 修复

- ExecutionCoordinator 记录进程保留锁的 Run/进程身份，与正常资源锁共用冲突语义。
- 本 Run 新动作与自己的保留进程锁冲突时返回 `process_resource_busy`，注明尚未执行及进程 ID，由模型选择读取、停止或稍后重新调用；不让整批一直等待。
- 进程管理工具使用 process 锁，保持可用；其他 Run 仍等原资源锁，只有确认进程退出/收拢后释放，不降级成无锁执行。
- Hook 使用同一检查，遵循原有各阶段故障策略，避免其等待本 Run 的后台进程锁。
- 工具说明补充：运行进程持续占锁、团队等待用 wait_agents、递归扫描限定范围并剪枝；不强制模型的业务分工，不限制任务总时长。
