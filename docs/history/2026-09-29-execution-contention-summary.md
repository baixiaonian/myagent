# 2026-09-29：只读并发、锁等待诊断、事件等待与摘要弹性预算

## 目的与现场依据

修复进度报告任务暴露的四项问题：Shell 一律占项目写锁、团队等待看不到阻塞来源、工具参数错误无法指导纠正、摘要刚超目标就取消。现场分析为 222 次模型请求、275 次 Shell 调用、22 分 31 秒存在锁等待；阶段时间重叠，不能简单相减当作优化收益。本轮不重新运行用户原任务，不产生真实模型费用。

## 当前实现

- exec_command 增加 readOnly。标准模式未指定时，只对可信程序/静态只读参数自动分类；复杂 Shell 可显式请求只读。只读 Worker 强制使用 OS 沙箱，权限和共享读锁限定 cwd、额外只读目录；不开放项目写入或网络。完全访问不自动降权，显式 readOnly 仍采用只读沙箱。任意未知普通 Shell 仍保留整个项目写锁。文件工具保持具体路径锁。Worker 权限缓存包含只读身份，沙箱不可用拒绝执行。
- 共用协调器记录锁持有/前序请求的 Run、调用、工具、进程和资源；Trace 保存 tool.lock_blocked。队列等待最多 5 秒后，尚未派发的工具返回 resource_busy，仍可由模型协调；不会取消持锁进程、提前放锁、自动重放或结束整个 Run。自身后台进程冲突继续使用 process_resource_busy。
- wait_agents 默认 30 秒、最大 120 秒，消息/状态事件唤醒；本 Run 持有项目进程锁时拒绝进入团队等待。主 Agent 收尾遇到同样问题会收到执行状态继续管理进程，不挂起自锁。读取/停止进程在同批遵守模型顺序。
- Ajv 校验投影字段、约束与纠正方法，不回显参数正文；明确 timeoutMs<=120000、waitMs<=10000，以及 command 与 cmd 的区别。无效参数无执行副作用。
- 摘要目标仍最多 2048 个估算 token；完整摘要发布上限为 min(8192, 可用输入预算的30%)。选择与分块按发布上限预留空间，写作目标低于原目标。普通超目标响应继续收齐终态和 usage，完整且确实缩小、最终上下文能容纳才发布；不截半份摘要，不自动追加模型修复请求。极端响应保留独立采集保护。发布失败但已收到的 usage 计入任务和上下文用量。模板 v2，已验证的 v1 摘要仍可恢复复用。

## 模块与边界

Kernel 仅扩展锁诊断回调和纯预算，唯一 Agent Loop 不变；Adapters 负责最终参数校验和真实只读隔离；Application 协调租约、团队等待和摘要；Server 注入共享等待检查。无新依赖，SQLite 仍为 v13，聊天 SSE 无版本变化，未修改用户配置。

这不是任意 Shell 的精确读写推断器；readOnly 通过真实隔离兑现，写入仍保守互斥。跨任务等待超时反馈不是死锁自动修复，更不代表副作用回滚。没有恢复任务总时限、累计字符配额或固定模型轮数。
